# コードレビューの7つの観点

「コードレビューの教科書」（技術評論社、著者：佐藤晶彦）をもとに作成

## 1. 設計

設計レビューで確認する観点

- アーキテクチャ
  - 採用しているアーキテクチャやフレームワークに沿った構造になっているか
    - 推奨される設計やベストプラクティスに沿っているか
  - レイヤー間の依存関係が適切か
    - ViewModelがデータベース層に直接依存するなど、本来依存すべきでないレイヤーへ依存していないか
  - API設計が適切か
    - RESTなどの設計原則に沿っているか
    - HTTPメソッドの選択が適切か
    - GETメソッドで登録・更新など、副作用を伴う処理を実行していないか
  - プレゼンテーション層の状態設計が適切か
    - エラー状態など、UIで必要となる状態を表現できているか
    - エラー表示や再試行の導線をUI側で扱える設計になっているか

- 責務設計
  - クラスや関数の責務が明確に分離されているか
    - 単一責任の原則（Single Responsibility Principle）に沿っているか
    - 1つのクラスや関数に複数の役割が混在していないか
  - 処理が適切なレイヤーやコンポーネントに配置されているか
    - Controllerなど、本来ビジネスロジックを持つべきでないレイヤーにビジネスロジックが混在していないか
  - 適切な単位で抽象化・集約されているか
    - 関連する処理がまとまっているか
    - 不要に細かく分割・抽象化されていないか

- 変更容易性
  - 変更や拡張の影響範囲が限定される設計になっているか
    - 特定のクラスや具体実装に強く依存していないか
    - 不必要な依存関係や緊密な結合がないか
  - 将来の変更を想定した過剰な設計になっていないか
    - 現時点で不要な実装や抽象化が含まれていないか
    - YAGNI（You Aren't Gonna Need It）の原則に違反していないか
  - 安定性が保証されない実装へ依存していないか
    - フレームワークやライブラリの非公開APIなどに依存していないか

- 一貫性
  - 設計方針がコード全体で統一されているか
    - 同様の責務を持つ処理が異なる設計方針で実装されていないか
  - 他のモジュールや既存システムとの整合性が保たれているか
    - 既存の設計パターンやインターフェースとの不必要な差異がないか
  - チームやプロジェクトの設計ガイドラインに沿っているか
    - プロジェクト固有のアーキテクチャルールに違反していないか

- エラー設計
  - エラーや例外が適切に分類されているか
    - 原因や種類の異なるエラーを同一の例外として扱っていないか
  - エラーの種類に応じて適切に処理できる設計になっているか
    - 呼び出し側が必要なエラーを識別し、適切なハンドリングを行えるか
  - 各レイヤーで扱うエラーの責務が明確か
    - 下位レイヤー固有の例外をそのまま上位レイヤーへ漏らしていないか

- テスト容易性
  - 単体テストを独立して実行しやすい構造になっているか
    - クラスや関数が多数の外部依存に強く結合していないか
  - 依存先をテスト用の実装へ差し替えられる構造になっているか
    - 必要に応じてinterfaceなどを介して依存性を注入できるか
    - モックやスタブへ置き換えられるか
  - テストのために過剰なセットアップを必要としていないか
    - 1つの処理を検証するために多数の関連コンポーネントを準備する必要がないか


## 2. 理解容易性

理解容易性レビューで確認する観点

- 簡潔性
  - 条件分岐やネストが必要以上に複雑になっていないか
    - 早期リターンなどによって処理の流れを単純化できないか
  - 条件判定や処理内容が長大になっていないか
    - 複雑な条件判定を意味のある単位で関数化できないか
  - 処理を必要以上に手続き的に記述していないか
    - コレクション操作など、より簡潔に表現できる方法がないか

- 可読性
  - コードの視覚的な読みやすさが保たれているか
    - 三項演算子などがネストし、読みづらくなっていないか
  - ロジックの流れを自然な順序で追えるか
    - 関連する処理が近くにまとまっているか
  - 値や処理の意図をコードから理解できるか
    - 意味のある数値がマジックナンバーとしてハードコーディングされていないか
    - 必要に応じて意図が分かる名前の定数として定義されているか

- 冗長性
  - 同じ処理やロジックが重複していないか
    - 同一・類似ロジックが複数ヶ所に分散していないか
  - 共通化すべき処理が適切に集約されているか
    - 共通ロジックとしてまとめることで変更箇所を減らせないか
  - 不要な処理が含まれていないか
    - 実行結果に影響しない処理や不要になったコードが残っていないか


## 3. 命名

命名レビューで確認する観点

- 責任・役割の明確性
  - クラス名から表現する概念や役割を理解できるか
    - UtilやManagerなど、役割が曖昧な名称になっていないか
  - 関数名から目的や動作内容を理解できるか
    - `process()`、`handle()`など、処理内容が分からない抽象的な名称になっていないか
  - 変数名から保持するデータや用途を理解できるか
    - 一時変数であっても用途が判断できないほど抽象的な名前になっていないか

- 操作・状態の明確性
  - 関数が何を行うかを名前から判断できるか
    - 状態を変更する処理なのか、データを取得する処理なのかが分かるか
  - データに対する操作方法を名前から判断できるか
    - オブジェクトを直接変更するのか、新しいオブジェクトを返すのかを区別できるか
  - 「何が、何を、どうするのか」が名前から伝わるか
    - 名前だけでは処理内容を推測できない状態になっていないか

- 命名規則
  - プロジェクトで定められた命名規則に従っているか
    - チーム内で同じ概念に異なる命名方法を使用していないか
  - 言語やフレームワークの標準的な命名規則に従っているか
    - クラス名には、その内容を表す名詞や名詞句を使用しているか
    - 関数名には、その動作を表す動詞や動詞句を使用しているか

- 表記
  - 単語のスペルが正しいか
    - タイポや一般的でない略語が含まれていないか
  - 英語として不自然な表現になっていないか
    - 英文法や単数・複数形などに不自然な点がないか


## 4. コードスタイル

コードスタイルレビューで確認する観点

- 自動チェック
  - Linterや静的解析ツールの違反が残っていないか
    - 自動的に検出可能なコード品質上の問題を放置していないか
  - コンパイラや型チェックの警告が残っていないか
    - 意図的に抑制している場合、その理由が妥当か

- コーディング規約
  - コードの表記やレイアウトが統一されているか
    - インデント、改行、空白などが一貫しているか
  - チームやプロジェクトのコーディング規約に準拠しているか
    - 独自の書き方を不必要に導入していないか

- アクセス範囲
  - クラス、関数、メンバーの公開範囲が必要最小限になっているか
    - 外部から利用する必要のないものをpublicにしていないか
  - テストのためだけに公開範囲を広げすぎていないか
    - テストコードから参照する場合でも必要最小限のアクセス範囲にとどめているか


## 5. 機能・性能

機能・性能レビューで確認する観点

- 機能要件
  - 実装が期待する仕様・挙動を満たしているか
    - 正常系で期待どおりの結果になるか
    - 異常系で期待どおりの結果になるか
  - 境界条件や特殊な条件でも正しく動作するか
    - null、空データ、最大・最小値などで不具合が発生しないか
  - 意図しない副作用が発生していないか
    - リストやオブジェクトなどの元データや共有状態を意図せず直接変更していないか

- 変更時の互換性・移行
  - 既存データや稼働中のシステムとの互換性が保たれているか
    - DBスキーマ変更やデータ移行によって、既存データの破損・欠損や既存機能の誤動作が発生しないか
    - 新旧バージョンが一時的に混在する場合でも正常に動作するか
  - マイグレーションが安全に実行できるか
    - 大量データの移行やスキーマ変更によって、長時間のロックやサービス停止を引き起こさないか
    - 移行途中の失敗や再実行によって、データ不整合や重複処理が発生しないか

- 処理効率
  - データ量の増加に対して処理時間が極端に悪化しないか
    - 要素数が多い場合に非効率な検索や繰り返し処理を行っていないか
  - 大量データを不必要に繰り返し処理していないか
    - 同じ計算や検索を何度も実行していないか
  - データベースアクセスが効率的か
    - N+1問題が発生していないか
  - ReactなどのUIフレームワークで、不要な再レンダリングや高コストな再計算が性能問題を引き起こしていないか
    - 状態管理やコンポーネント間の依存関係によって、変更と無関係なコンポーネントまで頻繁に再レンダリングされていないか

- リソース効率
  - 必要以上のデータをメモリ上に保持していないか
    - 大量データを一括で読み込む必要がない処理になっていないか
  - 必要以上のデータを取得していないか
    - 大量データを全件取得していないか
    - 取得件数を適切に制御できているか
  - CPU・メモリなどのリソースを過剰に消費していないか
    - 不要なオブジェクト生成や高コストな処理を繰り返していないか

- 非同期処理
  - 非同期処理の実行を適切に制御できているか
    - 必要以上に並列実行していないか
  - 処理のキャンセルを考慮しているか
    - 不要になった処理を継続し続けていないか
  - 完了タイミングや競合を考慮しているか
    - 処理順序によって結果が不定になる可能性がないか

- 通信量
  - 不要なデータを送受信していないか
    - 必要以上のフィールドやデータを取得・送信していないか
  - 大容量のデータやファイルを不必要にそのまま通信していないか
    - 分割、圧縮、必要部分のみの取得などを検討できないか

- リクエスト制御
  - 不必要に多くのリクエストを発生させていないか
    - 同じデータを短時間に繰り返し取得していないか
  - リトライが適切に制御されているか
    - ユーザーの意図しないタイミングで過剰な再リクエストが発生していないか
  - リトライ回数に上限があるか
    - 無限リトライが発生する可能性がないか

- セキュリティ
  - 入力値・インジェクション対策が適切か
    - AI/LLMを利用する場合、外部入力や取得コンテンツに含まれる指示を信頼せず、プロンプトインジェクションによる意図しない命令実行や機密情報漏洩を防止できているか 
    - SQLインジェクション対策としてプレースホルダーなどを利用しているか
    - 入力値の文字種・形式・範囲などを適切に検証しているか
  - 認証・認可が適切か
    - アクセス制御や認可に不備がないか
    - 認可に使用する情報をクライアント任せにせず、サーバー側で認証済みユーザー情報を取得しているか
    - IDOR（Insecure Direct Object Reference）など、他ユーザーのリソースへの不正アクセスを防止できているか
      - リソースIDを指定するAPIなどで、対象リソースに対するアクセス権限をサーバー側で検証しているか
  - 機密情報の扱いが適切か
    - APIキーやアクセストークンなどをコード内へ直接記述していないか
    - 機密情報を含むファイルをAIなど不要な処理から参照できないようにしているか
    - ログに個人情報や機密情報を出力していないか
    - ログにはIDなど必要最小限の情報だけを出力しているか
  - 認証情報の保存方法が適切か
    - パスワードを平文のままデータベースへ保存していないか
  - Webセキュリティ対策が適切か
    - CookieにSecure、HttpOnly、SameSiteなど必要な属性が設定されているか
  - 依存ライブラリの安全性が確保されているか
    - 既知の脆弱性を含むOSSライブラリを使用していないか


## 6. テスト

テストレビューで確認する観点

- テストケース設計
  - 正常系・異常系が必要な範囲でカバーされているか
    - API通信では、通信エラー、null応答、HTTPステータス別の例外処理などを確認しているか
  - 境界値が適切にカバーされているか
    - `>=`や`<=`などの比較では、境界値ちょうどとその前後を確認しているか
    - ゼロ、空文字列などの極端な値を確認しているか
  - 条件の組み合わせが適切にカバーされているか
    - 複数条件を持つロジックで代表的な組み合わせだけに偏っていないか

- 副作用の検証
  - 状態変更を伴う処理の結果を適切に確認しているか
    - 関数の呼び出しだけでなく、期待どおりに状態が変化したことまで確認しているか
  - 外部処理との連携結果を適切に確認しているか
    - 必要な外部処理が期待どおり呼び出されたことを確認しているか
  - 副作用が発生しないケースも確認しているか
    - 条件を満たさない場合に不要な更新や外部呼び出しが発生していないか

- テストコードの品質
  - テストコードが体系的に整理されているか
    - テスト対象や条件が理解しやすい構成になっているか
  - 重複したテストコードがないか
    - 共通セットアップや検証処理を適切に整理できないか
  - 不要なテストコードが残っていないか
    - 現在の仕様では意味を持たないテストが残っていないか

- テストの保守性
  - テストが実装詳細に強く依存していないか
    - privateメソッドをリフレクションで直接テストするなど、内部実装そのものを検証していないか
  - 実装変更によって必要以上に多くのテスト修正が発生しないか
    - 外部から観測できる振る舞いではなく内部構造に依存していないか
  - 同種のケースを効率的に追加・変更できるか
    - 必要に応じてパラメータライズドテストを活用しているか


## 7. ドキュメント

ドキュメントレビューで確認する観点

- 最新性
  - 実装とドキュメントの内容が一致しているか
    - ドキュメントコメントや補足コメントが現在の実装と矛盾していないか
  - 機能変更に合わせて関連ドキュメントが更新されているか
    - 機能の追加・変更・削除後に古い説明が残っていないか

- 明確性
  - 処理内容や仕様が具体的に記述されているか
    - 抽象的な説明だけでなく、必要な処理や挙動まで理解できるか
  - 使用方法を理解するために必要な情報が記述されているか
    - 共通コンポーネントなどでは、必要に応じて使用例が記載されているか
  - 読み手が前提知識を過度に補完しなくても理解できるか
    - 重要な前提条件や制約が省略されていないか

- 背景・意図
  - 設計意図や判断理由が記述されているか
    - 実装だけでは理由を理解できない設計判断の背景が残されているか
  - 特殊な実装の背景が記述されているか
    - 特殊な仕様に対応するためのコードについて、その理由が残されているか
  - 暫定実装の理由や今後の方針が記述されているか
    - やむを得ず暫定対応した箇所について、その理由や対応予定が残されているか

- 運用情報
  - セットアップに必要な情報が記述されているか
    - 必要な手順や依存関係が明示されているか
  - 外部依存に関する情報が記述されているか
    - OSSや外部APIなど、利用・運用に必要な情報が含まれているか
