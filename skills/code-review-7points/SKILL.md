# Code Review Skill

## 目的

コード変更をレビューし、実際に問題となる箇所を重要度付きで具体的に指摘する。

レビュー基準そのものはこのファイルに重複して記載せず、
必ず `references/code_review_7points.md` を参照する。

## Reference

レビュー開始時に、必ず以下を読む。

- `references/code_review_7points.md`

このReferenceをレビュー基準の一次情報として扱う。

Referenceに定義された7観点:

1. 設計
2. 理解容易性
3. 命名
4. コードスタイル
5. 機能・性能
6. テスト
7. ドキュメント

Referenceの全項目を機械的に列挙するのではなく、
変更内容に関連する観点を選び、コード上で実際に問題が確認できるものを指摘する。

## 基本方針

- 実際に問題となる箇所を優先して指摘する
- 指摘にはコード上の根拠を示す
- 問題の影響と改善方法を明確にする
- 推測と確認済み事実を区別する
- 好みの違いだけの指摘を避ける
- 将来の仮定だけに基づく過剰な抽象化を要求しない
- 変更と無関係な既存問題は原則として指摘しない
- 問題がなければ無理に指摘を作らない

## レビュー対象の把握

最初に、レビュー対象と変更の意図を把握する。

変更内容だけでなく、関連する既存コード、テスト、ドキュメント、プロジェクト固有のルールを確認し、変更の目的・影響範囲・制約を理解する。

確認範囲は変更内容との関連性に応じて判断する。ただし、レビューの妥当性を判断するために必要な情報を省略してはならない。

必要な情報を確認できない場合は、推測で補わず、その制約をレビュー結果に明示する。

PRやdiffが与えられている場合は、原則として変更箇所を中心にレビューする。
ただし、変更によって既存コードとの不整合や回帰が生じる可能性がある場合は、周辺コードも確認する。

## レビュー手順

### 1. 変更目的を理解する

diffだけを見て判断せず、変更によって何を実現しようとしているかを確認する。

例:

- 新機能
- バグ修正
- リファクタリング
- 性能改善
- テスト追加
- 設定変更

変更目的が不明な場合は、断定せず「意図が〜であれば」のように扱う。

### 2. Referenceに沿ってレビューする

`references/code_review_7points.md` を読み、
今回の変更に関連する観点を選んで確認する。

特に、次の優先順位で確認する。

1. 正しさ
2. セキュリティ
3. データ整合性
4. エラー処理
5. 性能・リソース
6. 設計・保守性
7. テスト
8. 命名・コードスタイル
9. ドキュメント

### 3. テストを確認する

変更に対するテストの妥当性を確認する。

テスト不足を指摘する場合は、
単に「テストが足りない」とせず、追加すべきケースを具体的に示す。

### 4. 実行可能な検証を行う

環境で可能な場合は、関連する検証を実行する。

例:

- unit test
- integration test
- lint
- formatter check
- type check
- build

レビュー対象と無関係な広範囲の修正は行わない。

## サブエージェントの利用

変更規模が大きい、複数レイヤーにまたがる、または専門的な観点を並列に確認する価値がある場合は、
レビューをサブエージェントへ分担してよい。

小規模な変更では、原則として単一エージェントでレビューする。
観点ごとに機械的にサブエージェントを起動しない。

分担する場合は、以下の4グループを基本とする。

### Architecture

担当:

- 設計
- 責務分離
- 依存関係
- エラー設計
- テスト容易性
- 既存アーキテクチャとの一貫性

### Correctness & Security

担当:

- 機能・性能
- 正常系 / 異常系
- 境界条件
- 状態変更 / 副作用
- 非同期処理 / 競合
- DBアクセス
- 外部API
- セキュリティ
- プロンプトインジェクションを含むAI/LLM固有のリスク

### Maintainability

担当:

- 理解容易性
- 命名
- コードスタイル
- 重複
- 複雑度
- 公開範囲
- 保守性

### Tests & Documentation

担当:

- テスト
- テストケース設計
- 境界値 / 異常系 / 副作用の検証
- テストコードの品質と保守性
- ドキュメント
- README / API仕様 / コメント / 運用情報の更新

### サブエージェントへの指示

各サブエージェントは、担当観点についてのみFinding候補を返す。

次を必ず守る。

- `references/code_review_7points.md` をレビュー基準として参照する
- diffだけで判断せず、必要に応じて周辺コード・テスト・プロジェクトルールを確認する
- 問題がなければ「指摘なし」としてよい
- 担当観点について必ずFindingを出す必要はない
- コード上の具体的な根拠がない指摘は出さない
- 推測の場合は断定しない
- 変更と無関係な既存問題は原則として扱わない
- 重大度は暫定値として扱い、最終決定はメインエージェントに委ねる

### メインエージェントによる統合

サブエージェントの結果を単純に連結して最終回答にしてはならない。

メインエージェントは、すべてのFinding候補について以下を行う。

1. コード上の根拠を再確認する
2. 変更内容との関連性を確認する
3. 重複した指摘を統合する
4. 同一の根本原因に由来する指摘を可能な限りまとめる
5. 推測だけの指摘や誤検知を除外する
6. 重大度を再評価する
7. 改善案が実際に適用可能か確認する

最終的なFindingの採用可否と重大度は、メインエージェントが決定する。

### 分担の判断目安

サブエージェントの利用を検討する例:

- 変更ファイル数が多い
- UI / Application / Domain / Infrastructureなど複数レイヤーにまたがる
- DB、非同期処理、認証・認可、外部APIなど複数の専門領域を含む
- 大規模なリファクタリング
- 複数の機能を同時に変更するPR
- diffが大きく、単一エージェントでは観点の見落としリスクが高い

単一エージェントを優先する例:

- 数行〜数十行程度の小規模な修正
- 単純なバグ修正
- 命名変更
- コメントやドキュメントのみの変更
- 対象範囲が1つの関数や1つのコンポーネントに限定される変更

## 重大度

各指摘に以下の重大度を付ける。

### Critical

マージすると重大な障害やセキュリティ事故につながる可能性が高い。

例:

- 認証・認可の欠落
- データ破壊
- 機密情報漏洩
- サービス全体が停止する不具合

### High

主要機能の誤動作、明確な回帰、重大な運用問題につながる。

例:

- 一般的な入力で誤った結果になる
- 例外処理不足で主要処理が失敗する
- DB整合性が壊れる
- 非同期競合で結果が不定になる

### Medium

特定条件での不具合、保守性や性能への現実的な悪影響がある。

例:

- 境界値で失敗する
- N+1
- 責務混在により変更影響が大きい
- 重要ケースのテスト不足

### Low

直ちに不具合にはならないが、明確な改善価値がある。

例:

- 読みづらい命名
- 軽微な重複
- 将来バグにつながりやすい分かりづらい構造

### Nit

任意修正。

原則として、チーム規約違反など明確な根拠がある場合のみ使用する。
好みだけのNitは出さない。

## 指摘を書く条件

指摘は、以下をすべて満たす場合に出す。

1. コード上に具体的な根拠がある
2. 何が問題なのかを具体的に説明できる
3. その問題が発生する入力・状態・タイミング・環境などの条件を説明できる
4. その条件で発生した場合の影響を説明できる
5. 修正方法または望ましい方向性を示せる
6. 変更対象と関連している

発生条件を具体的に特定できず、問題が起こる可能性だけを推測している場合は、原則としてFindingにしない。
コードだけでは発生条件を確認できない場合は、断定せず確認事項として扱う。

## 指摘フォーマット

各指摘は以下の情報を含める。

```text
[Severity] 短いタイトル

対象: path/to/file.py:L10-L18
観点: 設計 / 理解容易性 / 命名 / コードスタイル / 機能・性能 / テスト / ドキュメント

問題:
何が問題なのか。

発生条件:
どの入力・状態・タイミング・環境などで問題が発生するのか。

影響:
その条件で問題が発生した場合、ユーザーやシステムにどのような影響があるのか。

改善案:
どのように修正するのがよいか。
必要なら短いコード例を示す。
```

コードレビューUI上でインラインコメントを書く場合は、
テンプレートをそのまま冗長に使わず、
「問題 → 影響 → 改善案」が伝わる簡潔な文章にする。

## 出力形式

最終結果は以下の順序で出力する。

### 1. Review summary

2〜5文程度でまとめる。

- 変更の目的
- 全体評価
- 重要なリスク
- マージ可否の判断材料

### 2. Findings

重大度の高い順に並べる。

```markdown
## Findings

### [High] エラー応答を成功として保存している

`src/foo.py:42-51`

**観点:** 機能・性能

`response.json()` の結果をHTTPステータスに関係なく保存しているため、
4xx/5xx時にもエラーレスポンスが正常データとして永続化されます。

`response.raise_for_status()` 相当の確認を保存前に行い、
エラー時は保存処理へ進まないようにしてください。
```

### 3. Missing tests

不足テストがある場合のみ記載する。

追加すべきテストケースを具体的に示す。

### 4. Optional improvements

マージを妨げない改善案がある場合のみ記載する。

重要なFindingsと混ぜない。

## 問題が見つからない場合

問題が見つからない場合は明示する。

```markdown
## Findings

重大な問題は見つかりませんでした。
```

そのうえで、確認した主要観点や、実行できなかった検証があれば簡潔に記載する。

## 不確実な指摘

コードだけでは判断できない場合は断定しない。

悪い例:

> このAPIは必ずタイムアウトします。

良い例:

> 呼び出し側でタイムアウトが設定されていることを確認できませんでした。
> 共通HTTPクライアント側で設定されていない場合、応答待ちが長時間継続する可能性があります。
